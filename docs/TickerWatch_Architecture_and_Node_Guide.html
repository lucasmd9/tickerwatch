System overview and presentation framing

TickerWatch is a stateful research assistant for a ten-stock demonstration universe. It collects news, proposes stock relevance, produces bounded research cases, prioritises recorded positions, tracks what changed and keeps evidence, hypotheses, future checks and price observations available through Telegram. It supports a Bloomberg Trading Challenge team’s research process; it is not connected to Bloomberg or a trade-execution account.

A useful opening sentence: “We moved from asking a bot for financial information to maintaining an evidence-linked research workflow: what happened, why our team should care, what we should check next, and what changed since we last looked.”

The inspected published snapshot contains nine workflows, 126 operational nodes and nine sticky notes: one main orchestrator, seven callable helpers and one separate error handler. Model resources count as operational nodes but are not sequential steps on the main data path. Canvas notes execute no business logic.

Data contracts and persistent state

Most workflow boundaries pass one structured n8n item. The important fields are cfg (policy and service configuration), action/original_action/args (request), run_id, universe, state, rows/nextRows and dirty. Fan-out branches temporarily emit per-source or per-job items; the main workflow deliberately restores/merges the parent context.

dirty is a list of intended writes, conceptually {table, key, value}. Code nodes may update the in-memory state and append dirty records; the next Store write makes them durable. A node name containing “save” does not necessarily mean an external write occurs inside that Code node.

The durable event identity is its canonical URL. Short TW-… references help Telegram users select a case; a collision/ambiguity fails safely rather than choosing a random record. Candidate matching, accepted analysis and human review are different states. Reading a case does not independently verify its facts.

The briefing snapshot compares against the latest fully delivered report. It includes a bounded set of recent validated cases plus related portfolio, journal, result and calendar state. First use establishes a baseline; later changes can report additions, changed evidence, review state or research activity. It is a research delta, not a byte-for-byte archive of the whole database.

1. Main workflow — TickerWatch

The main workflow is the orchestrator: it authorises requests, loads shared state, calls specialised helpers, chooses a command branch, saves results and manages delivery. It contains 44 operational nodes and three canvas notes. A feature does not necessarily have its own node: portfolio, thesis, review and command rendering functions live inside the large command formatter.

The three entry points converge before routing. Consequently, a Telegram command first loads the database and passes through market and calendar helpers. Those helpers decide whether the particular action needs a refresh; not every command makes new external requests. The shared context then carries the configuration, requested action, universe, stored records and pending writes through the branches.

Manual / 07:00 Paris / Telegram → Settings → Authorise → Store read
  → Market Observations → Store write → Calendar Discovery → Store write
  → Dispatch → Router
    collect → sources → match → reserve → persist → analyse → build → persist
    earnings → reserve → persist → evidence search → persist → reply
    reply → format command → persist
    retry → select eligible saved delivery
  → sequential delivery → refresh state → persist in-flight → Telegram → persist result

01 Run collection now manualTrigger

Manual entry

Starts a collection from the n8n editor. With no Telegram message, parsing uses the configured manual action or collection default. This is an operational trigger, not a separate demo mode.

02 Daily 07 Paris scheduleTrigger

Scheduled entry

Cron 0 7 * * * starts the same pipeline at 07:00 Europe/Paris, following that timezone’s daylight-saving changes. The host, Docker and required services must be running.

03 Telegram commands telegramTrigger

Webhook entry

Receives bot messages. Receiving an update is not sufficient authorisation: the next Code node checks the private owner chat before accessing research data or models.

04 Settings set

Configuration

Creates the configuration used by downstream nodes: database, owner, model, collection caps, evidence budgets and analysis versions. Keeping these together makes policy changes visible rather than scattered through HTTP nodes.

05 Authorise and parse code

Security and input contract

Checks configuration and owner chat; unauthorised messages return no items, stopping execution. Splits slash commands and arguments, removes an optional @bot suffix and maps unknown text to help. Creates action, args, requested_at, run_id, from_telegram and operation=read. It does not ask an LLM to interpret commands.

06 Load database executeWorkflow

Call Store: read

Loads Universe and the six research/state tables into one context, including row indexes for future updates. Later functions work on this loaded snapshot and mark changed records in dirty.

07 Refresh market observations executeWorkflow

Call Market Observations

Checks whether collection or /outcomes requires fresh Yahoo daily history. Cached results pass through without another price request. Returns observations plus any dirty Meta records.

08 Save market observations executeWorkflow

Call Store: write

Commits those price/reference changes before proceeding. Separating calculation from persistence makes the helper reusable and keeps database writes centralised.

09 Discover calendar events executeWorkflow

Call Calendar Discovery

Checks the action and per-company cache, then gathers eligible Yahoo dates and selected issuer-calendar evidence. Returns dated observations, explicit coverage gaps and pending Meta writes.

10 Save calendar observations executeWorkflow

Call Store: write

Persists calendar observations so both the current response and later commands can use the same saved evidence.

11 Dispatch command code

Resolve request

Preserves original_action and resolves listings from ticker/stock_id and optional exchange. Ambiguous or unknown stocks produce guidance. Most commands become the generic reply action while original_action tells the formatter which feature to render.

12 Command router switch

Four-way switch

Routes collect, earnings, reply or retry. This is deterministic branching; the model cannot choose arbitrary tools or workflow paths.

13 Plan source requests code

Collection branch: plan

Deduplicates the universe by issuer and selects up to ten company queries using a persisted round-robin cursor. Adds BBC Business, BBC World and a Google macro-news RSS search. With ten issuers this normally produces thirteen feed requests. A larger universe rotates through ten issuers per run rather than exhaustively scanning everything.

14 Fetch Sources executeWorkflow

Call Fetch Sources for each request

Runs the source helper once per request and waits for its result. Each result has normalised articles and source-coverage metadata. The current plan uses RSS; the helper also retains a Yahoo news branch.

15 Queue new articles code

Normalise identity and lifecycle

Canonicalises URLs, removes tracking parameters and skips exact URL duplicates. Missing dates go to review; articles older than seven days or more than one day in the future are stale. Saves source coverage and cursor progress. Version fields allow controlled reprocessing when matching or analysis rules change. URL cleanup does not eliminate every syndicated duplicate.

16 Match Universe executeWorkflow

Call Match Universe

Adds direct company or evidenced thematic candidates and marks articles pending or filtered. Matching identifies candidates for analysis; it does not establish a proven stock impact.

17 Reserve budgets and queue code

Choose bounded work

Ranks pending items by recorded held weight, editorial relevance and recency, then diversifies issuers and similar titles. Selects at most three analysis events and two candidate stocks per event. Reserves eligible public-article and earnings-search allowances before external calls. Can schedule an earnings-only enrichment job without repeating impact analysis.

18 Persist pending work executeWorkflow

Call Store: write

Saves queued events and reservations before expensive work. This protects against repeating the same unrecorded reservation after failure, although Google Sheets is not a transactional database.

19 Select analysis jobs code

Fan out jobs

Emits one item for each selected analysis/enrichment job. When there are no jobs it emits a no_jobs sentinel so briefing construction can still run.

20 Has job? if

Guard analysis

Routes real jobs to Analyse Event and the sentinel directly to briefing construction. A quiet news day can therefore still produce portfolio, calendar and coverage information.

21 Analyse Event executeWorkflow

Call Analyse Event per job

Waits for each child result. The node continues through regular output on error so the builder can record incomplete work as review rather than losing the whole report. Child results are subsequently joined back to the persisted parent context.

22 Build and save briefing code

Assemble research and pending writes

Combines job results with the context saved before analysis. Stores article evidence, earnings, analyses and impact links; missing or invalid results become review records. Selects up to three recent priority stories, preferring relevant held names and issuer diversity. Writes summary first, then mechanism, next check, counterpoint, case references, portfolio, changes, agenda, calendar, outcomes and coverage. Computes a delivered-baseline research snapshot and creates pending delivery chunks. Despite its name, this Code node prepares writes; the following Store call commits them.

23 Save briefing before delivery executeWorkflow

Call Store: write

Persists the briefing, pending chunks, events and run metadata before Telegram is contacted. This makes a saved report available for recovery and later inspection.

24 Prepare delivery code

Select chunks

On collection, collects eligible pending/failed reports from the recent three-day window; on retry, uses the selected saved report. Items held for ambiguous delivery/content review are not blindly resent. Identical already-delivered same-day signatures can suppress a repeated collection report.

25 Reserve earnings search code

Earnings branch: cache and budget

Uses successful earnings evidence cached for 24 hours or unavailable evidence cached for 15 minutes. Otherwise reserves three search attempts/credits if the daily allowance permits. A budget refusal returns deferred status, not invented figures.

26 Save search reservation executeWorkflow

Call Store: write

Persists the reservation before Evidence Search. The reservation concerns search resources, not a global LLM token allowance.

27 Search allowed? if

Guard retrieval

Calls Evidence Search only when a new search is permitted. Cache hits and deferred requests proceed directly to response handling.

28 Evidence Search executeWorkflow

Call reported-facts helper

Retrieves primary issuer material and uses a model plus deterministic quote checks to return reported figures, or an explicit unavailable result.

29 Save earnings response code

Merge result

Restores the reserved parent context and merges new evidence. Cache hits or deferred searches do not overwrite saved evidence with an empty result.

30 Persist earnings executeWorkflow

Call Store: write

Commits evidence and related state before the reply is delivered.

31 Earnings reply code

Format two evidence categories

Shows calendar observations separately from reported earnings facts. A Yahoo earnings date does not become issuer-verified financial evidence. Reported facts include their period, basis and source where accepted; missing evidence is stated plainly.

32 Format command reply code

Ordinary-command branch

Renders saved research and handles controlled writes for portfolio, review, thesis and catalyst commands. It resolves short case references safely, updates relevant records in memory and emits dirty writes. It contains deterministic feature functions rather than a free-form chatbot or an LLM call. Command replies are ephemeral delivery items, separate from persistent briefing delivery tracking.

33 Call 'TickerWatch • Store' executeWorkflow

Call Store: command writes

Persists any changes made by the command formatter before sending its confirmation. A read-only command has no dirty writes and simply passes through.

34 Select failed delivery code

Retry branch

Selects the latest eligible saved pending/failed delivery with attempts below three. Does not rerun news collection or the LLM and does not automatically resend ambiguous-outcome chunks held for review.

35 Deliver chunks sequentially splitInBatches

Delivery loop

Processes one delivery item at a time. The false eligibility branch returns to the loop so an already-sent item does not prevent later eligible chunks being handled. The done output reaches Finished.

36 Read delivery context code

Prepare fresh read

Sets operation=read for the current delivery item so the latest saved delivery state can be checked immediately before sending.

37 Refresh delivery state executeWorkflow

Call Store: read

Reloads current records rather than trusting the earlier collection snapshot. This reduces stale overwrites and duplicate sends when delivery state has changed.

38 Mark in flight code

Prepare durable send attempt

Checks saved chunk eligibility, changes an eligible persistent chunk to in-flight, increments attempts and records a timestamp. Ephemeral command messages do not modify a persistent briefing record.

39 Eligible delivery chunk? if

Skip sent or held items

Only eligible items enter persistence and sending. Already-sent or review-held persistent chunks are skipped and the loop continues.

40 Persist in flight executeWorkflow

Call Store: write

Records the attempt before Telegram is called. If the process stops at this boundary, an operator sees an uncertain/incomplete attempt rather than an apparently untouched message.

41 Send Telegram telegram

External delivery

Sends escaped HTML with labelled source anchors, disabled link previews and no n8n attribution. A message has at most six source anchors. Errors continue into result classification instead of an unconditional node-level retry.

42 Record delivery result code

Classify outcome

A returned message_id marks success. A definite rejection can be marked failed; a timeout/socket problem with uncertain remote outcome is held for review rather than assumed unsent. Aggregates chunk states into the report delivery state.

43 Persist delivery result executeWorkflow

Call Store: write

Saves message IDs, attempts and final/partial state before returning to the loop. This supports controlled recovery; it is not a distributed exactly-once guarantee.

44 Finished noOp

End marker

No-operation endpoint on the completed loop output. It marks a finished delivery traversal, not independent proof that every external service succeeded.

Presenter line: “The main workflow controls the lifecycle. It loads state once for research, calls specialists, commits before costly work, and commits again before and after delivery.”

The briefing uses approximately 3,400-character chunks with a display cap of 26,000 characters. Its full-report splitter preserves Unicode boundaries and prefers newlines. Smaller command/earnings formatting paths have their own chunking logic. The daily signature includes selected/source state and portfolio revision, but does not explicitly encode every possible intraday outcome or calendar field; do not promise that every external change forces an automatic resend.

2. Store — persistence boundary

Store is the single persistence adapter. Its input is the shared context with operation=read or write. A read adds universe, state, rows and nextRows; a write consumes dirty records and returns the updated context. It uses authenticated Google Sheets HTTP calls rather than asking a model to read or update the database.

Input → Read?
  yes → Read database → Decode database
  no  → Build updates → Changes? → Commit updates → Return saved context
                                  no changes ────→ Return saved context

01 Input executeWorkflowTrigger

Subworkflow contract

Accepts the parent item, including cfg and operation. Write operations require the loaded row context so updates can target existing records or append safely.

02 Read? if

Read/write switch

Separates a full database read from a batch of explicit dirty-record updates. There is no arbitrary database query generated by an LLM.

03 Read database httpRequest

Sheets batchGet

Retrieves seven tabs in one batch: Universe, Events, ImpactLinks, Earnings, Runs, Briefings and Meta. Universe is conventional header-based data; the other six use key in column A and JSON in column B.

04 Decode database code

Validate and hydrate

Checks required Universe headers, listing identity fields and duplicates. Parses JSON records and builds state maps, record-to-row indexes, next append rows and an empty dirty list. Malformed data raises an error rather than being silently ignored.

05 Build updates code

Validate write set

Deduplicates dirty entries by table and key, checks an allowlist, requires row context and resolves updates versus appends. Rejects oversized JSON over 45,000 characters or rows beyond 10,000. This adapter does not write Universe changes through the normal dirty-record path. Stored event candidates are compacted to stock_id, match_type and matched.

06 Changes? if

Avoid empty API calls

Only calls Sheets when there are actual cell updates. Read-only command flows pass through without a pointless write request.

07 Commit updates httpRequest

Sheets batchUpdate

Writes the prepared ranges using RAW input. RAW prevents stored strings being interpreted as spreadsheet formulas. Successful writes clear pending dirty changes in the returned context.

08 Return saved context code

Restore parent data

Returns the research/delivery context rather than the Google HTTP response body, so downstream nodes keep their expected contract.

Why this architecture: one adapter means row allocation, validation and write policy are maintained in one place. JSON records make nested analysis, histories and chunk states practical in a small Sheets-backed project.

Tradeoff: the database is easy to inspect but has no relational constraints, transactions or distributed lock. Full reads and JSON cells limit scale. Production concurrency is configured to one, which reduces overlap within that execution path; it does not protect against every manual/CLI/external writer. Candidate compaction also means not every in-memory provenance field remains on a reloaded Event; related Universe/ImpactLinks records may carry richer provenance. A missing candidate source in /case should not be described as a verified source.

3. Fetch Sources — source normalisation

Fetch Sources isolates news-provider differences. The caller gives it a source request and receives a common article list plus coverage diagnostics. The current daily planner chooses RSS feeds; the Yahoo news path is retained as an alternative capability.

Input → RSS? → Read RSS → Normalise RSS
             no → Pace Yahoo → Yahoo news → Normalise Yahoo

01 Input executeWorkflowTrigger

Request contract

Receives cfg and a source descriptor, plus collection cursor/coverage context from the planner.

02 RSS? if

Choose adapter

Selects the RSS path for RSS sources and the Yahoo path for the alternative source type.

03 Read RSS rssFeedRead

Read feed

Fetches feed items from the requested RSS URL. The headline and feed description are source material, not proof that the complete article has been read.

04 Normalise RSS code

Common article schema

Normalises title, URL, publication time and a snippet capped at 3,000 characters. Keeps up to twenty articles per feed, records received count/truncation/errors and labels evidence_scope=headline_and_feed_summary.

05 Pace Yahoo wait

Provider pacing

Waits before a Yahoo news request. It belongs to the retained Yahoo source path, not the current RSS-first collection plan.

06 Yahoo news httpRequest

MCP tool request

Calls the local Yahoo MCP get_market_news tool through HTTP. This is distinct from the direct Yahoo chart endpoint used for prices.

07 Normalise Yahoo code

Decode provider response

Parses JSON carried in MCP/SSE text, handles nonstandard numeric tokens and the “no recent news” case, checks for a news array and emits the same article/coverage shape. Company relevance is still checked later; a provider response is not assumed to be ticker-specific.

Presenter line: “This helper converts different providers into one contract. Downstream matching does not need to know whether an item came from RSS or MCP.”

Failure visibility matters: unavailable/truncated feeds become coverage information rather than an apparently complete news scan.

4. Match Universe — relevance before model spending

This deliberately small helper has two operational nodes. It reduces the universe of possible stock relationships before spending model capacity. Matching is deterministic and uses configured company aliases or reviewed economic-exposure tags.

Input → Match names and evidenced exposures

01 Input executeWorkflowTrigger

Articles plus universe

Receives queued events, listing/issuer metadata and reviewed exposure configuration.

02 Match names and evidenced exposures code

Filter and attach candidates

Rejects numerical stock-price forecasts and stock-picking/opinion headlines. Uses normalised whole-phrase company aliases of at least four characters with selected collision/subsidiary guards. Where there is no direct company match, thematic exposure requires a source URL and a valid reviewed_on date. Country alone is never sufficient. Themes include fuel costs, oil revenue, US/China demand, funding, semiconductors and tariffs. Returns candidate stock/issuer identities, match type and rationale, sets pending or filtered status and marks Events dirty.

Why before the LLM: it bounds candidate identities, lowers cost and makes the model explain a proposed relationship instead of inventing an arbitrary company list.

Limits: lexical matching can still confuse an ordinary word with a company. An Apple-fruit headline, for example, can match Apple textually; later analysis may identify it as unrelated, and explicit unrelated mechanisms are excluded from held-position promotion. Reviewed exposure is a sourced hypothesis about relevance, not proof that this particular news event materially changes earnings.

5. Analyse Event — constrained LLM reasoning

Analyse Event turns one queued article and a bounded candidate list into a structured research case. It can enrich the article with permitted public text and optionally retrieve reported earnings evidence. The LLM writes a summary and possible mechanisms, while code owns selection, validation, state and delivery.

Input → article reservation? → find approved matching page → read/extract/keep
  → Article context → earnings enrichment? → Evidence Search if reserved
  → Prepare evidence and prompt → earnings only? → Return earnings enrichment
  otherwise → Wait → Explain possible impacts → Validate analysis → contract check
    valid / non-correctable failure → Return analysis
    invalid nonempty output → Wait1 → Correct once → Validate correction → Return analysis
Groq Chat Model / Groq Chat Model1 connect to the corresponding chains as model resources.

01 Input executeWorkflowTrigger

One job

Receives the event, at most two selected candidate stocks, evidence/cache context and previously saved budget reservations.

02 Article lookup reserved? if

Budget gate

Allows public-article discovery only when the parent reserved an article lookup. Otherwise the case proceeds using available cached article text or the headline/feed summary, with evidence scope retained.

03 Find public article httpRequest

Discovery search

Uses local SearXNG to search for the exact headline. Results locate possible pages; search snippets alone do not become full-article evidence.

04 Choose matching public article code

Source and title checks

Requires HTTPS, an approved news/issuer domain and sufficient title-token overlap (at least 0.45). Chooses a permitted likely match rather than fetching arbitrary links returned by a search engine.

05 Public article located? if

Optional enrichment branch

Reads a permitted match if available. Otherwise continues through the shared Article context without pretending enrichment succeeded.

06 Read public article httpRequest

Public HTTP retrieval

Fetches the selected page through ordinary HTTP. This is a best-effort public-text lookup, not a paywall bypass or guaranteed browser-rendered article reader.

07 Extract article text html

HTML extraction

Extracts readable text from returned HTML for the subsequent evidence checks.

08 Keep article evidence code

Quality check and cache

Rejects short text below 500 characters, poor title/body overlap below 0.5 and denial/paywall/captcha content. Keeps up to 12,000 characters with URL, check time and scope; the impact prompt uses up to 5,000. Invalid page text is not promoted to article evidence.

09 Article context noOp

Merge boundary

No-op convergence point for enriched and non-enriched paths. It does not perform an additional model call.

10 Enrich earnings? if

Reserved optional retrieval

Calls Evidence Search only when the job requires and has reserved earnings enrichment. Previously saved usable evidence can be supplied without a new search.

11 Evidence Search executeWorkflow

Call primary-facts helper

Returns checked issuer-source facts or explicit unavailable evidence; its separate process is described in the next section.

12 Prepare evidence and prompt code

Bound model inputs

Builds a prompt from title (up to 600 characters), snippet (1,800), public article (5,000), at most two allowed candidates and compact checked earnings. Treats source text as untrusted content. Instructs the model not to invent exposures, entities, quarters, forecasts, recommendations or beat/miss claims.

13 Earnings only? if

Avoid redundant impact generation

If this is a later enrichment-only job, returns the earnings update without reclassifying the original article or generating another impact analysis.

14 Return earnings enrichment code

Small child result

Returns enrichment data and identifiers to the parent. The parent merges it with its saved context and persists it.

15 Wait wait

Pace initial generation

Deliberately waits 62 seconds before the first impact model call. This reduces pressure on provider token-per-minute allowances and explains why fresh collection is slower than reading a saved report.

16 Groq Chat Model lmChatGroq

Initial model resource

Supplies Groq-hosted openai/gpt-oss-20b at temperature 0.1 with a 3,200-token completion cap. This resource connects to the chain through an AI-model connection, not as a sequential data-processing node.

17 Explain possible impacts chainLlm

Initial LLM chain

Generates event_type, a plain-language summary, priority and candidate impacts. Each impact contains stock_id, direction, mechanism, uncertainty, original source_url, watch_next and counterpoint. The output is a research interpretation, not an automated trade.

18 Validate analysis code

Deterministic output gate

Parses JSON/code fences and checks required fields, enum values, cardinality, lengths, candidate IDs, uniqueness and exact original event URL. Adds heuristics against numerical forecasts and unsupported proper names/quarters. An unsupported quarter in a research task can be replaced with a deterministic task while preserving rejected_watch_next; unsupported factual quarter claims reject the analysis.

19 Valid JSON contract? if

Accept or bounded repair

Passes valid output to Return analysis. A provider error or empty output is not repaired by another speculative generation. A nonempty invalid structured response may receive one correction attempt.

20 Wait1 wait

Pace correction

Applies another 62-second wait before the optional repair call. The correction is bounded rather than an open retry loop.

21 Groq Chat Model1 lmChatGroq

Correction model resource

Uses the same Groq model and low temperature, with a 4,200-token completion cap for the repair chain.

22 Correct once chainLlm

Single repair chain

Receives the failed contract and validation feedback and attempts one corrected JSON response. It does not create an unbounded agent conversation.

23 Validate correction code

Reapply output rules

Checks the repaired response with the validation contract. A second invalid result remains review work rather than being accepted just because two model calls were made.

24 Return analysis code

Constrained result contract

Returns event identity, available article evidence, candidates, earnings, errors and either accepted analysis with analysed status or a review result. The parent owns durable persistence and briefing selection.

Presenter line: “The model supplies semantic interpretation: summary, causal hypothesis, uncertainty, next research question and counterargument. Code restricts which stocks it can discuss and rejects output that fails the contract.”

The checks establish structure and traceability, not independent truth. A model can still misunderstand a story or propose a weak economic mechanism while producing perfectly valid JSON. The user reviews evidence and makes the investment judgment.

6. Evidence Search — reported earnings with quote checks

This helper has a different purpose from impact analysis. It looks for primary issuer material and extracts a very small number of reported facts. It does not infer quarterly results from a generic financial-data capability, and it does not turn a search snippet into verified revenue or EPS.

Input → inspect tools → capability check → issuer search → raw evidence?
  yes → Keep primary page text
  no → local search → approved release? → read → extract → adapt → keep
  → Primary text available?
    yes → pace → extract facts with Groq → verify quoted evidence
    no → Unavailable earnings

01 Input executeWorkflowTrigger

Issuer-scoped request

Receives the resolved company/issuer, configured primary domains and the parent’s reserved search context.

02 Inspect Yahoo tools httpRequest

Capability discovery

Calls tools/list on the local Yahoo MCP service. Available tool names are inspected rather than assuming the service exposes every requested earnings field.

03 Quarterly capability check code

Avoid false capability claims

Recognises that a get_financial_statements tool does not by itself establish a usable quarterly-results contract. The current implementation continues to primary issuer-release retrieval.

04 Search issuer releases httpRequest

Primary-domain search

Queries Tavily using curated investor-relations domains plus sec.gov, requesting raw content and at most three basic-search results. The HTTP node has bounded retry settings; reservations are coarse allowances rather than a provider billing audit.

05 Search returned raw evidence? if

Evidence gate

Uses returned primary page text if present. If search failed or produced no usable raw material, tries the local discovery fallback.

06 Search local issuer fallback httpRequest

Alternative discovery

Uses local SearXNG when the primary search path does not provide evidence. This provides resilience to retrieval/TLS problems without fabricating missing data.

07 Select approved release code

Conservative release selection

Checks approved domains, company aliases and results/quarter/earnings-release wording. Excludes forecasts, estimates and transcripts as substitutes for the intended issuer release.

08 Approved release found? if

Fetch only approved match

Allows an ordinary page read only for a qualifying release; otherwise proceeds with explicit missing evidence.

09 Read approved issuer release httpRequest

Primary HTTP retrieval

Fetches the selected issuer page. Source access can still fail or require client rendering; the workflow does not treat discovery as successful fact retrieval.

10 Extract primary page text html

HTML to text

Extracts primary-page text for quote selection. It is separate from the article-enrichment extractor because this path supports reported-fact verification.

11 Adapt retrieved evidence code

Unify fallback shape

Converts fetched or missing fallback output into the same evidence representation used by the main search path.

12 Keep primary page text code

Select bounded excerpts

Keeps up to three pages, at most 66,000 characters each for verification. Builds exact contiguous excerpts totalling at most 5,200 characters, using windows around accounting/period language and avoiding Outlook sections. Assigns excerpt IDs so extraction can cite a real text fragment.

13 Primary text available? if

Do not generate without evidence

Only calls the fact-extraction model when usable primary text exists. A missing page leads to Unavailable earnings.

14 Pace earnings model wait

Provider pacing

Waits 62 seconds before the earnings-generation call to reduce token-per-minute pressure.

15 Groq Chat Model lmChatGroq

Fact-extraction resource

Uses Groq-hosted openai/gpt-oss-20b, temperature 0.1 and a 4,000-token completion cap. It is attached to the extraction chain as a model resource.

16 Extract reported facts chainLlm

Small extraction task

Asks for at most two facts, preferring recent total revenue and GAAP diluted EPS. Requires precise source value, period, currency/units/basis and excerpt ID. A future release date is only eligible when explicitly announced in issuer text. This is not a consensus beat/miss calculation.

17 Verify quoted evidence code

Check against retrieved page

Attaches the actual selected excerpt, checks a normalised contiguous quote against page text, and checks value/period/basis context. Rejects forecast contexts and inappropriate comparative/table values; enforces current-period and GAAP/non-GAAP distinctions. A future release date must parse, be future and have announcement wording. Records rejected counts and extraction/provider failures rather than guessing.

18 Unavailable earnings code

Explicit missing result

Returns status unavailable with retrieval/capability context and no invented figures. Missing earnings facts do not imply that the separate calendar helper cannot find an upcoming provider date.

Output: issuer/company, checked_at, evidence_checked or unavailable status, accepted facts with source URLs and retrieval notes. The parent caches successful evidence for 24 hours and unavailable evidence for 15 minutes.

These are quote-supported extraction checks, not an accounting audit. They reduce common hallucinations but do not prove every table interpretation. Explain “source-checked reported facts,” not “all earnings independently verified.”

7. Market Observations — reference outcome tracking

This helper answers what happened to prices after observation began. It uses direct Yahoo Finance chart requests, not an LLM and not the Yahoo MCP news tool. It tracks stock-versus-local-benchmark reference returns; it does not calculate the Bloomberg competition portfolio’s actual performance.

Input → Refresh needed?
  yes → Plan Yahoo requests → Fetch Yahoo daily history → Record reference outcomes
  no  → Use saved market observations

01 Input executeWorkflowTrigger

State and requested action

Receives universe, saved Meta observations and the action that initiated the main workflow.

02 Refresh needed? if

Six-hour gate

Refreshes for collect or outcomes when no market refresh exists or the previous attempt is at least six hours old. Other commands use saved values. A failed refresh also has a recorded attempt time, avoiding immediate repeated pressure.

03 Plan Yahoo requests code

Symbols and benchmarks

Plans up to the first ten universe listings and deduplicates their benchmark symbols. Uses SPY for US listings, Euro Stoxx 50 for selected euro markets, FTSE for London, Nikkei for Tokyo, Hang Seng for Hong Kong and SMI for Switzerland, with expected currencies.

04 Fetch Yahoo daily history httpRequest

Direct chart API

Requests one year of daily Yahoo chart history, including dividends/splits, sequentially with a 250 ms interval and a 15-second timeout. Continues on individual request errors so usable series can still be processed.

05 Record reference outcomes code

Validate series and calculate

Requires usable symbol/currency/timezone metadata and positive close/adjusted-close values. Conservatively excludes the current exchange-local date, rejects stale series older than six days and keeps a bounded history. Establishes the baseline at the latest common completed stock/benchmark session first observed; later uses common-date adjusted closes to calculate stock return, benchmark return and their percentage-point difference. Retains the original reference date/raw close and marks failed refreshes stale. Creates separate thesis references keyed to thesis creation. Returns dirty Meta records for the parent to save.

06 Use saved market observations code

Cache path

Returns the existing context without network calls or fresh writes. Saved timestamps and stale flags remain meaningful; a cache hit is not labelled a new market observation.

Calculation: stock return = latest adjusted close / baseline adjusted close − 1. Benchmark return uses the same common dates. Relative difference = stock return − benchmark return, displayed in percentage points. Adjusted baselines can be recalculated from the current series for corporate actions while preserving the original observed reference.

The benchmark must have compatible currency; GBp/GBX handling normalises comparison units. No FX conversion, trade execution, fees or portfolio weighting is added. A missing baseline beyond the available one-year window is not silently reset. A price rise does not prove the thesis was correct. Local benchmarks are not necessarily the competition benchmark.

8. Calendar Discovery — dates with provenance

Calendar Discovery separates upcoming events from reported historical earnings. It combines structured Yahoo fields and a curated issuer-calendar registry. Every date retains its source category: provider estimate/scheduled/reported, issuer-supported calendar date, or a separately entered team plan. A provider-scheduled event is not automatically issuer-confirmed.

Input → Plan calendar checks → Calendar refresh needed?
  yes → Yahoo requests → Read Yahoo fields → Keep responses
      → Issuer requests → Read issuer pages → Validate and retain evidence
  no  → Use cached calendar evidence

01 Input executeWorkflowTrigger

Action plus saved evidence

Receives configuration, universe, action/arguments and saved calendar records in Meta.

02 Plan calendar checks code

Scope and cache plan

Eligible actions include collect, catalysts, earnings and stock. A company-specific earnings/stock/catalysts request narrows the listings; the general board uses up to ten. /catalysts status reads cache only. Successful provider results use a six-hour cache and failed attempts a fifteen-minute cooldown. Fixed issuer URLs and request caps bound retrieval.

03 Calendar refresh needed? if

Refresh/cache switch

Skips external work when no planned check needs renewal. This avoids fetching every issuer page whenever someone opens a saved board.

04 Yahoo calendar requests code

Build explicit POST payloads

Builds get_company_info requests for the local Yahoo MCP HTTP endpoint. Request construction is kept separate from HTTP expressions, reducing ambiguity around dynamic body/method handling.

05 Read Yahoo calendar fields httpRequest

Provider retrieval

Sends the planned POST requests. This service is the local MCP provider; it differs from the direct public Yahoo history GET used by Market Observations.

06 Keep Yahoo calendar responses code

Decode and align

Parses JSON or SSE-wrapped responses, checks errors and symbol identity, and preserves plan/result alignment. Reads earningsTimestamp/start/end, estimate flags, ex-dividend and dividend dates where present. Wrong-company responses are not attached to the requested listing.

07 Issuer calendar requests code

Curated primary-page plan

Builds GET requests for known issuer-calendar pages rather than treating arbitrary search headlines as event dates. Plans remain bounded and source-specific.

08 Read issuer calendar pages httpRequest

Primary calendar retrieval

Fetches the planned issuer pages. Blocking, client-side rendering and unfamiliar layouts can leave a source unavailable or unparsed, which is retained in coverage information.

09 Validate and retain calendar evidence code

Parse conservatively and persist intent

Validates provider dates, ignores past dates and bounds future dates to a year. Earnings timestamps use the exchange timezone; dividend timestamps encoded as UTC calendar days retain that day. Preserves date windows and estimate flags. Parses supported JSON-LD events, bounded table rows with explicit dates/titles and a Tencent-specific adapter. Does not infer an event from an article publication date or freely associate nearby text. Retains source labels, stale/error states and dirty Meta records. Display dedup prefers issuer evidence for the same stock/type/date and flags conflicts.

10 Use cached calendar evidence code

Reuse saved board

Returns existing observations without claiming a fresh check. Stale saved evidence can be retained for a limited period with its age visible rather than silently replaced with guesses.

Interpretation: a false Yahoo estimate flag is labelled provider_scheduled; an estimated/unknown date or window remains provider_estimate. Dividend fields are provider_reported. An issuer date without a confirmed time remains date-only. Team-entered catalyst dates remain unverified team plans.

The inspected deployment had usable provider checks for ten listings but issuer parsing was incomplete; ASML, SAP, MC and NESN had no accepted upcoming earnings observation in that snapshot. This is a coverage limitation, not a promise that those companies have no future events. The board is not a complete corporate-actions calendar. Primary pages can be blocked or require a new parser, and unavailable dates are not invented.

9. Error Handler — production failure notification

This workflow is registered as the main workflow’s error handler. It covers unhandled production execution errors, while deliberately handled per-source/model/delivery failures stay visible in their normal records. It is separate from LLM JSON correction and delivery recovery.

Production error → Error Settings → Sanitise error → Load error log
  → Append error record → Persist error log → Notify owner

01 Production error errorTrigger

Error Trigger

Receives the failed production execution context when n8n invokes the registered error workflow. It is not a polling health check.

02 Error Settings set

Configuration

Supplies the database and owner notification configuration required for logging the failure.

03 Sanitise error code

Minimal failure record

Keeps execution ID, workflow, failing node and time while avoiding a raw credential-bearing error dump in the user notification.

04 Load error log executeWorkflow

Call Store: read

Loads the current state and row indexes so the failure can be recorded through the same persistence policy as normal runs.

05 Append error record code

Build audit entry

Adds a Runs record keyed by the failed execution with error status and minimal diagnostic metadata.

06 Persist error log executeWorkflow

Call Store: write

Commits the error record before sending its notification, if Sheets is reachable.

07 Notify owner telegram

Telegram alert

Tells the owner that an execution failed and should be inspected in n8n. This path itself depends on working Sheets access and Telegram delivery, so it is not an independent guaranteed monitoring system.

Presenter line: “Failures are handled at different levels: source gaps stay in coverage, invalid analyses become review cases, uncertain sends are held, and unexpected production failures reach the error workflow.”

What the LLM actually does, and the limits

Two kinds of semantic work use the LLM: impact interpretation in Analyse Event, and reported-fact extraction in Evidence Search. The impact path has an initial chain and one optional correction chain. Each chain has its attached Groq model resource. Earnings extraction has one chain and one model resource. Model nodes are configuration dependencies; they are not extra independent generations each time an item passes them.

Groq hosts openai/gpt-oss-20b. Using that model name does not mean the workflow calls the OpenAI API. The current model temperature is 0.1. Completion caps are 3,200 tokens for initial impact, 4,200 for correction and 4,000 for earnings extraction. Input text is also bounded before prompting.

The configured collection caps permit three initial impact analyses, up to three corresponding corrections and at most one earnings enrichment per run: up to seven logical generations in that bounded path. This is not a universal daily cap. Provider/SDK transport retries can create additional HTTP attempts, and separate manual commands/runs can add usage. Search-budget reservations do not meter Groq tokens.

The published workflow has no complete global daily LLM-token ledger. Actual rate/token allowances depend on the configured Groq account and can change; no specific account quota is claimed here. The explicit 62-second waits are pacing, not a guarantee that provider throttling cannot occur. Existing saved reports and deterministic dashboard commands are much faster than fresh retrieval and analysis.

No LLM is needed to calculate portfolio percentages, reference returns, benchmark differences, date-cache eligibility, command routing, delivery state or human evidence labels. Keeping these deterministic makes the system easier to explain and audit.

Two end-to-end examples for your explanation

Example A: scheduled news collection

  1. At 07:00 Paris the schedule enters Settings and parsing. No Telegram message means a collection action.
  2. Store loads the database. Market/calendar helpers refresh only when eligible and their dirty records are saved.
  3. The router selects collection. Thirteen feed requests are planned for the current ten issuers plus macro feeds; Fetch Sources normalises their results and reports coverage.
  4. Queueing canonicalises article URLs, checks dates and preserves lifecycle. Match Universe attaches direct or reviewed-exposure candidates.
  5. Suppose an issuer-results headline has a relevant held candidate. The parent selects it within the three-event cap, reserves optional article/earnings retrieval, and saves those decisions before external work.
  6. Analyse Event may obtain approved public article text and primary earnings evidence. After pacing, Groq produces a summary and bounded impact hypotheses. Code accepts the contract, repairs once, or returns a review case.
  7. The builder merges results into the persisted context, selects up to three priority stories and adds portfolio, research deltas, agenda, calendar, outcomes and gaps. Store commits the pending report.
  8. The delivery loop refreshes each chunk’s latest state, persists in-flight status, sends Telegram and records the result. Only a fully delivered report becomes the normal changes baseline.

Example B: a student opens /portfolio and then saves a thesis

  1. Telegram sends the command through the same authorised entry. Store reads saved state; the market/calendar helpers normally skip unnecessary refreshes for these actions.
  2. Dispatch retains original_action=portfolio and routes to reply. Format command reply builds the deterministic dashboard from the saved allocation; it does not call the LLM.
  3. Store has no dirty updates for a simple display. The ephemeral message goes through delivery without changing briefing delivery history.
  4. A subsequent /thesis command validates the listing and hypothesis/invalidation text, creates a journal record in Meta, and saves it before confirmation.
  5. The team can attach a case using /evidence. The snapshot and fingerprint preserve what was assessed; a later changed case prompts reassessment. Later market refreshes can start a separate reference observation for that thesis.

These examples explain why the same entry and delivery infrastructure can support very different features without giving the model control over state mutation.

Presentation sequence and likely questions

Suggested explanation order: show the main canvas and its three entry points; explain shared state and four branches; open Fetch Sources and Match Universe; spend most technical detail on Analyse Event and Evidence Search; then show calendar, outcomes and Store; finish with delivery/error handling and the user-facing research lifecycle. You do not need to read every Code function aloud.

On each node say three things: what enters, what decision/transformation happens, and what leaves. The node cards in this guide provide those talking points in route order. Model-resource cards are called out separately so you do not describe an AI connection as a normal execution edge.

“Is it an AI agent?”
It is a controlled workflow using LLM chains for interpretation and extraction. Code chooses tools, branches and state mutations.
“What if the model invents something?”
Candidate IDs, output shape, source URL and selected content claims are checked; primary financial facts require quote support. Invalid output gets one repair or review status. These gates reduce errors but cannot prove an economic interpretation correct.
“Why does a collection take time?”
Fresh retrieval is external work and model calls deliberately wait 62 seconds. Reading a saved briefing is a different, faster path.
“Is this real portfolio performance?”
No. Holdings are a labelled fictional allocation snapshot. Outcomes are observed stock/benchmark references, with no trades, FX, fees or portfolio P&L.
“Why are some earnings dates missing?”
Yahoo can omit or retain past fields; issuer pages can be blocked, rendered dynamically or unsupported. The system records coverage gaps instead of guessing.
“Why Google Sheets?”
It is inspectable and economical for the bounded project. A larger multi-user production system should use stronger transactional persistence and more targeted reads.
“Can it handle 150 stocks?”
The planner can rotate company queries, but the tested demonstration is ten stocks. Wider full coverage, runtime and quota capacity have not been established by this implementation.
“Will retry duplicate a message?”
Saved chunk state, fresh reads and ambiguous-outcome holds reduce duplication. External delivery still cannot be guaranteed exactly once.
Closing line: “The value is the connected research process: prioritised news, evidence-linked hypotheses, a dated agenda, observable follow-up and an audit of what changed. The investment decision stays with the team.”
